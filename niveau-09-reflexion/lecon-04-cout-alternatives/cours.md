# Leçon 4 — Coût et alternatives

> Les trois leçons précédentes ont montré ce que la réflexion **permet**. Celle-ci mesure ce qu'elle
> **coûte**, puis présente les deux outils qui la remplacent dans la plupart des cas : les **génériques**,
> quand le code est le même pour plusieurs types, et la **génération de code**, quand il dépend de la
> structure d'un type connu à la compilation. La conclusion du niveau tient en une phrase : la réflexion
> est le bon outil pour les bibliothèques qui doivent accepter des types inconnus, et rarement ailleurs.

## Objectifs

1. Mesurer le coût réel de la réflexion, et savoir d'où il vient.
2. Réduire ce coût quand la réflexion est nécessaire (analyse du type mise en cache).
3. Remplacer la réflexion par des génériques quand c'est possible.
4. Écrire un générateur de code avec `go generate`, `go/parser` et `text/template`.
5. Choisir entre les trois, avec des critères explicites.

## Explication

### Ce que coûte la réflexion

Mesuré, somme du champ `Price` de 10 000 livres :

| Méthode | Temps | Rapport |
|---|---|---|
| boucle directe, dans une fonction | 13,5 µs | 1 |
| générique `SumBy(books, func(b Book) float64 { return b.Price })` | 13,5 µs | 1 |
| réflexion, index du champ calculé une fois (`FieldByIndex`) | ≈ 105 µs | ≈ 8 |
| réflexion, `FieldByName("Price")` à chaque élément | ≈ 680 µs | ≈ 50 |

Et, pour produire les destinations d'un `Scan` (leçon N8 L2) d'une struct de 5 champs :

| Méthode | Temps | Allocations |
|---|---|---|
| code **généré** | 39 ns | 1 |
| réflexion avec plan mis en cache | 177 ns | 1 |
| réflexion, analyse des balises à chaque appel | 1 090 ns | 5 |

D'où vient le coût :

- **l'analyse du type** (parcourir les champs, lire et découper les balises, chercher un champ par son
  nom) : de loin le plus cher, et identique à chaque appel. Le **cache** par `reflect.Type` le supprime
  (×6 ici) ;
- **les `reflect.Value`** : chaque accès vérifie la sorte, les droits (`CanSet`, champ exporté), et
  passe par des indirections que le compilateur ne peut pas supprimer ;
- **les conversions vers `any`** (`Interface()`), qui allouent souvent ;
- **l'absence d'optimisation** : pas d'*inlining*, pas de vectorisation, pas de suppression des
  vérifications de bornes à travers un code réflexif.

Remarque de méthode : une première mesure, avec la boucle « directe » écrite dans le corps du
benchmark sur une variable **globale**, donnait 30 µs — plus lent que la version générique. Placée dans
une fonction qui reçoit la slice en paramètre, elle tombe à 13,5 µs. Un benchmark mesure le code **tel
qu'il est compilé** ; écrire le code mesuré comme il le serait en vrai, dans une fonction. Le niveau 11
revient sur ces pièges.

### Alternative 1 : les génériques

Avant Go 1.18, une fonction « pour tout type » s'écrivait avec `any` et `reflect`. Aujourd'hui, si le
**code** est le même pour tous les types, et que seule la **donnée** change, c'est un générique (niveau 3) :

```go
func SumBy[T any](xs []T, f func(T) float64) float64 {
	s := 0.0
	for _, x := range xs {
		s += f(x)
	}
	return s
}
```

Vérifié à la compilation, aussi rapide que le code direct (mesuré), lisible. Ce que les génériques **ne
savent pas** faire : parcourir les champs d'un type, lire ses balises, se brancher sur sa structure. Dès
que le code dépend de la **forme** du type (`Book` a cinq champs, dont `CreatedAt` qui s'appelle
`created_at` en base), il faut soit de la réflexion à l'exécution, soit de la génération de code à la
compilation.

### Alternative 2 : générer le code

L'idée : faire le travail de la réflexion **une fois, avant la compilation**, et écrire le résultat sous
forme de code Go ordinaire, versionné avec le reste. Les outils :

- `go/parser` et `go/ast` lisent un fichier source et en donnent l'arbre syntaxique : types, champs,
  balises (sous forme de texte : `reflect.StructTag(raw).Lookup("db")` sert aussi à les lire ici) ;
- `text/template` (N4 L8) produit le code ;
- `go/format.Source` le met en forme comme `gofmt` — et rend une erreur si le code généré est
  syntaxiquement faux, ce qui attrape les bugs du générateur ;
- la directive `//go:generate go run ../cmd/dbgen …` dans le fichier source, et la commande
  `go generate ./...`, qui exécute toutes ces directives.

Conventions de l'outillage Go :

- le fichier généré commence par la ligne `// Code generated by … DO NOT EDIT.` (forme exacte reconnue
  par les outils : `go vet`, les éditeurs et les relectures de code savent qu'il ne faut pas le modifier
  à la main) ;
- il est **versionné** : `go build` n'exécute **pas** `go generate`, un utilisateur du paquet doit pouvoir
  compiler sans le générateur ;
- la CI vérifie qu'il est à jour : relancer `go generate` puis `git diff --exit-code` (niveau 12).

C'est la technique de `stringer` (méthodes `String()` pour les constantes), de `sqlc` (N8 L8), des
générateurs de code Protobuf et gRPC (N7 L12).

### Choisir

| Situation | Outil |
|---|---|
| Même algorithme, types différents (conteneurs, `Map`/`Filter`, tri, cache) | **génériques** |
| Code qui dépend de la structure de **vos** types, connus à la compilation (accès aux bases, sérialisation à fort volume, *mocks*) | **génération de code** |
| Bibliothèque qui doit accepter des types **inconnus** d'elle (encodeurs, chargeurs de configuration, outils de test) | **réflexion**, avec cache de l'analyse |
| Quelques types connus, un comportement par type | une **interface**, ou un `switch` de types |
| Prototype, outil interne, volume faible | la réflexion est acceptable si elle simplifie vraiment |

Coûts cachés à mettre dans la balance : la réflexion déplace les erreurs de la compilation vers
l'exécution ; la génération ajoute une étape de construction et un outil à maintenir ; les génériques
peuvent rendre les signatures difficiles à lire s'ils sont empilés.

## Exemple

Un générateur qui lit les balises `db` d'un fichier source et produit la liste des colonnes et les
destinations de `Scan` — le travail que GORM fait par réflexion à chaque requête (N8 L8). Puis un test qui
vérifie que le code généré et la version réflexive donnent le même résultat, et un benchmark.

```go
// Fichier : model/model.go
package model

//go:generate go run ../cmd/dbgen -file model.go -out model_db.go

import "time"

type Book struct {
	ID        int64     `db:"id"`
	Title     string    `db:"title"`
	Author    string    `db:"author"`
	Price     float64   `db:"price"`
	CreatedAt time.Time `db:"created_at"`
	cache     string    // pas de balise : ignoré
}
```

```go
// Fichier : cmd/dbgen/main.go
// dbgen lit un fichier Go et génère, pour chaque struct dont des champs ont une balise db,
// les fonctions Columns et ScanDest. Aucune réflexion à l'exécution : tout est décidé ici.
package main

import (
	"bytes"
	"flag"
	"go/ast"
	"go/format"
	"go/parser"
	"go/token"
	"log"
	"os"
	"reflect"
	"strconv"
	"strings"
	"text/template"
)

type field struct{ Name, Column string }
type model struct {
	Name   string
	Fields []field
}

var tmpl = template.Must(template.New("").Parse(`// Code generated by dbgen; DO NOT EDIT.

package {{.Package}}
{{range .Models}}
// Columns{{.Name}} est la liste des colonnes, dans l'ordre de ScanDest.
const Columns{{.Name}} = "{{range $i, $f := .Fields}}{{if $i}}, {{end}}{{$f.Column}}{{end}}"

// ScanDest rend les destinations de Scan, dans l'ordre de Columns{{.Name}}.
func (x *{{.Name}}) ScanDest() []any {
	return []any{ {{- range $i, $f := .Fields}}{{if $i}}, {{end}}&x.{{$f.Name}}{{end -}} }
}
{{end}}`))

func main() {
	file := flag.String("file", "", "fichier source")
	out := flag.String("out", "", "fichier généré")
	flag.Parse()

	fset := token.NewFileSet()
	f, err := parser.ParseFile(fset, *file, nil, 0)
	if err != nil {
		log.Fatal(err)
	}
	var models []model
	ast.Inspect(f, func(n ast.Node) bool {
		ts, ok := n.(*ast.TypeSpec)
		if !ok {
			return true
		}
		st, ok := ts.Type.(*ast.StructType)
		if !ok {
			return true
		}
		m := model{Name: ts.Name.Name}
		for _, fl := range st.Fields.List {
			if fl.Tag == nil || len(fl.Names) != 1 {
				continue
			}
			raw, _ := strconv.Unquote(fl.Tag.Value) // la balise telle qu'écrite dans le source
			col, ok := reflect.StructTag(raw).Lookup("db")
			if !ok || !fl.Names[0].IsExported() {
				continue
			}
			m.Fields = append(m.Fields, field{fl.Names[0].Name, strings.TrimSpace(col)})
		}
		if len(m.Fields) > 0 {
			models = append(models, m)
		}
		return false
	})
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, map[string]any{"Package": f.Name.Name, "Models": models}); err != nil {
		log.Fatal(err)
	}
	src, err := format.Source(buf.Bytes()) // même mise en forme que gofmt
	if err != nil {
		log.Fatalf("code généré invalide : %v\n%s", err, buf.Bytes())
	}
	if err := os.WriteFile(*out, src, 0o644); err != nil {
		log.Fatal(err)
	}
}
```

```go
// Fichier : model/model_db.go
// Code generated by dbgen; DO NOT EDIT.

package model

// ColumnsBook est la liste des colonnes, dans l'ordre de ScanDest.
const ColumnsBook = "id, title, author, price, created_at"

// ScanDest rend les destinations de Scan, dans l'ordre de ColumnsBook.
func (x *Book) ScanDest() []any {
	return []any{&x.ID, &x.Title, &x.Author, &x.Price, &x.CreatedAt}
}
```

```go
// Fichier : model/reflect.go
package model

import (
	"reflect"
	"strings"
	"sync"
)

// ScanDestReflect fait la même chose que ScanDest, par réflexion, à chaque appel.
func ScanDestReflect(ptr any) (string, []any) {
	v := reflect.ValueOf(ptr).Elem()
	t := v.Type()
	var cols []string
	var dest []any
	for i := range t.NumField() {
		col, ok := t.Field(i).Tag.Lookup("db")
		if !ok || !t.Field(i).IsExported() {
			continue
		}
		cols = append(cols, col)
		dest = append(dest, v.Field(i).Addr().Interface())
	}
	return strings.Join(cols, ", "), dest
}

// La même chose, avec l'analyse du type mise en cache (ce que font les bibliothèques sérieuses).
type plan struct {
	cols  string
	index []int
}

var plans sync.Map

func ScanDestCached(ptr any) (string, []any) {
	v := reflect.ValueOf(ptr).Elem()
	t := v.Type()
	p, ok := plans.Load(t)
	if !ok {
		var cols []string
		var idx []int
		for i := range t.NumField() {
			if col, ok := t.Field(i).Tag.Lookup("db"); ok && t.Field(i).IsExported() {
				cols, idx = append(cols, col), append(idx, i)
			}
		}
		p, _ = plans.LoadOrStore(t, plan{strings.Join(cols, ", "), idx})
	}
	pl := p.(plan)
	dest := make([]any, len(pl.index))
	for i, fi := range pl.index {
		dest[i] = v.Field(fi).Addr().Interface()
	}
	return pl.cols, dest
}
```

```go
// Fichier : model/model_test.go
package model

import (
	"reflect"
	"testing"
)

func TestGeneratedMatchesReflect(t *testing.T) {
	var b Book
	cols, dest := ScanDestReflect(&b)
	if cols != ColumnsBook {
		t.Fatalf("colonnes : %q contre %q", cols, ColumnsBook)
	}
	gen := b.ScanDest()
	if len(gen) != len(dest) {
		t.Fatalf("%d destinations contre %d", len(gen), len(dest))
	}
	for i := range gen {
		// Mêmes adresses : les deux pointent vers les mêmes champs de b.
		if reflect.ValueOf(gen[i]).Pointer() != reflect.ValueOf(dest[i]).Pointer() {
			t.Errorf("destination %d différente", i)
		}
	}
}

var sink []any

func BenchmarkScanDest(b *testing.B) {
	var book Book
	b.Run("genere", func(b *testing.B) {
		for b.Loop() {
			sink = book.ScanDest()
		}
	})
	b.Run("reflexion", func(b *testing.B) {
		for b.Loop() {
			_, sink = ScanDestReflect(&book)
		}
	})
	b.Run("reflexion-cache", func(b *testing.B) {
		for b.Loop() {
			_, sink = ScanDestCached(&book)
		}
	})
}
```

## Explication du code

| Élément | Ce qui compte |
|---|---|
| `//go:generate go run ../cmd/dbgen …` | La commande à exécuter, à côté du code qu'elle concerne ; lancée par `go generate`, jamais par `go build`. |
| `parser.ParseFile` + `ast.Inspect` | Le générateur lit le **source**, pas des valeurs : il voit les types sans les exécuter. |
| `strconv.Unquote(fl.Tag.Value)` puis `reflect.StructTag(raw).Lookup` | La balise est un littéral dans l'AST ; une fois décodée, on réutilise l'analyseur de balises standard. |
| `fl.Names[0].IsExported()` | Même règle qu'à l'exécution : `cache` n'a pas de balise, et un champ non exporté ne serait de toute façon pas accessible depuis un autre paquet. |
| `template` + `format.Source` | Code produit lisible et vérifié syntaxiquement ; une erreur du générateur est signalée avec le code fautif. |
| `// Code generated by dbgen; DO NOT EDIT.` | La convention reconnue par l'outillage. |
| `ColumnsBook` constante | Utilisable dans une requête : `"SELECT " + ColumnsBook + " FROM books"`, sans risque de décalage avec `ScanDest`. |
| `TestGeneratedMatchesReflect` | Compare les **adresses** des destinations : le code généré pointe vers les mêmes champs que la version réflexive. |
| `ScanDestCached` | La réflexion « bien faite » : analyse une fois par type (`sync.Map`), puis seulement l'accès aux champs. |
| Écarts mesurés | Généré ×28 plus rapide que la réflexion naïve, ×4,5 que la réflexion avec cache ; 1 allocation (la slice rendue) contre 5. |

## Erreurs fréquentes

1. **Utiliser `reflect` pour un algorithme générique** que les génériques exprimeraient.
2. **Réanalyser le type à chaque appel** dans du code réflexif fréquent.
3. **Ne pas versionner le code généré**, ou le modifier à la main.
4. **Oublier de régénérer** après une modification du type : le code généré décrit l'ancienne version.
   (Les tests comme `TestGeneratedMatchesReflect`, ou la vérification en CI, l'attrapent.)
5. **Un générateur qui produit du code mal formé** sans `format.Source` pour le signaler.
6. **Optimiser la réflexion sans mesure** : souvent le coût est ailleurs (réseau, base, analyse de texte,
   comme dans le décodeur CSV de la leçon 2).
7. **Écrire le code mesuré directement dans le corps du benchmark** sur des globales : la mesure ne
   représente pas le code réel.

## Bonnes pratiques Go

- Dans l'ordre : types concrets, interfaces, génériques, génération, réflexion.
- Réflexion : analyse du type une fois, en cache ; accès par index, jamais par nom dans une boucle.
- Génération : `go:generate` à côté du code, en-tête `DO NOT EDIT`, fichier versionné, vérifié en CI.
- Un test qui compare la sortie générée à une référence (réflexive ou écrite à la main).
- Mesurer (N5 L6) avant et après ; ne garder que ce qui change la mesure de façon significative.

## Ce que je dois retenir

- La réflexion coûte de ×8 à ×50 (et plus) par rapport au code direct ; l'essentiel du coût est
  l'analyse du type, que le cache supprime.
- Génériques : même code, types différents, coût nul à l'exécution — mais aucun accès à la structure du
  type.
- Génération : le travail de la réflexion fait une fois, avant la compilation ; code ordinaire, vérifié,
  rapide.
- `go generate` n'est pas lancé par `go build` : le code généré est versionné et vérifié en CI.
- La réflexion reste le bon outil pour les bibliothèques qui doivent accepter des types qu'elles ne
  connaissent pas.
